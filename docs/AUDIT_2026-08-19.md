# S0 — Blocks shipping

### S0-1 · `env.txt` ships inside the artifact; on web it is a public URL

`pubspec.yaml` declares `- env.txt` under `flutter: assets:`; `main.dart:10` loads it via
`rootBundle`. It holds `ARCGIS_URL`, `GOOGLE_MAPS_API_KEY`, and `HCT_BASE_API_URL`.

- **Android:** `unzip` the AAB, read `assets/flutter_assets/env.txt`. Plaintext.
- **Web:** the asset is emitted to `build/web/assets/` and served over HTTP.
  `https://<your-domain>/assets/env.txt` returns all three values to anyone who types the URL.
  No decompilation, no tooling.

The Directions **Web Service** API supports only IP referrer restrictions — not Android/iOS app
restrictions — so an extracted key cannot be locked down.

`docs/SECURITY.md` currently asserts local assets are "not accessible via HTTP — no server-side
exposure risk." That is exactly inverted on web.

**`GOOGLE_MAPS_API_KEY` and `ARCGIS_URL` must be treated as compromised** as of the first published build, and rotated.
`--dart-define` is **not** a fix — it obfuscates, it does not hide. The only fix is a server-side
proxy. See `REMEDIATION_PLAN.md` P0-1.

### S0-2 · The repository cannot be built from a clean clone

Six independent blockers. These affect a **fresh clone only** — this machine has all the ignored
files on disk, which is why the local baseline runs. That is precisely the danger: the breakage is
invisible to the one person who could notice it.

| # | Problem | Effect |
|---|---|---|
| a | `assets/data/{stops,schedules,routes_wgs84}.json` gitignored but declared as assets | Flutter fails hard (`No file or variants found for asset: …` — they are declared as individual files, not a directory). Build aborts before compilation. |
| b | `env.txt` gitignored but declared as an asset | Same hard failure. |
| c | `gradle-wrapper.jar`, `gradlew`, `gradlew.bat` untracked (`android/.gitignore`) | Android build fails immediately. The wrapper is *meant* to be committed. |
| d | `analysis_options.yaml` gitignored (`.gitignore:58`) | CI would run `flutter analyze` with default lints. Every quality gate the team believes is enforced is invisible. Nothing in this file is sensitive. |
| e | Parent repo tracks `flutter_app` as a gitlink with **no `.gitmodules`**, pinned to `8cf96b3`, which is **not an ancestor of HEAD** — it sits on the pre-purge history (22 commits) while HEAD has 46, sharing none | Cloning the parent yields an empty directory. `git submodule update --init` has no URL to fetch. |
| f | `*.freezed.dart` / `*.g.dart` gitignored (correct) but `build_runner` unenforced | Mandatory manual step, no CI to catch omission. |

The README's own setup instructions cannot work.

Note (a): "proprietary, not for public repo" already fails on its own terms — the data ships in
every published binary and is extractable from it.

### S0-3 · Release builds silently fall back to debug signing

`android/app/build.gradle.kts`:

```kotlin
signingConfig = if (keystorePropertiesFile.exists()) signingConfigs.getByName("release")
                else signingConfigs.getByName("debug")
```

With no `key.properties`, `flutter build appbundle --release` **exits 0** and emits a minified,
shrunk, debug-signed AAB. Nothing in the log distinguishes it from a real release. It is caught
only at Play Console upload — after the artifact has been shared, attached to a ticket, or given
to testers. On CI the debug keystore is regenerated per runner, so the signature is
non-deterministic.

Must fail loudly. Also: `signingConfigs { }` is nested *inside* `buildTypes { }` — it resolves
today by Gradle Kotlin DSL scoping, but it is misleading and fragile.

### S0-4 · `targetSdk` / `minSdk` / `compileSdk` are unpinned — 12 days before a hard deadline

All three read `flutter.*Version`, so the API level the app declares to Play is a property of
**whichever Flutter SDK is installed on the build machine**, not of this repository.

[Google Play requires new apps to target API 36 from **31 Aug 2026**](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en)
— twelve days from this audit. Whether you comply is currently determined by a developer's local
`flutter upgrade` state, with no diff in git to explain a rejection. An extension to 1 Nov 2026
can be requested via the Play Console.

Also contradictory: `flutter_launcher_icons` declares `min_sdk_android: 21` while Flutter's
current `minSdkVersion` is 24.

`test/widget_test.dart:16` imports `package:hubcity_transit_flutter/src/shared/widgets/main_scaffold.dart`.
**`lib/src/shared/` does not exist.**

Precise scope, because an earlier draft overstated this:

- The stale import exists **only in the uncommitted working tree**, alongside a second
  regression: `dio_provider.dart` has had its `if (!kIsWeb)` guard around the `User-Agent`
  header removed, reverting the web fix from `fd84719`.
- Dart test files compile independently, so the other tests are **not** taken down with it:
  the measured result is `+8 -1`. Only the exit code is non-zero.

`app_router.dart:72` still carries a dartdoc referencing the same ghost class, which is how the
deletion was left half-finished.

`docs/LLM_HANDOVER.md` instructs a future agent to believe in `shared/widgets/main_scaffold.dart`
and a Fares tab. Whether that is how the import returned is **speculation, not established** —
but a stale handover doc that misdirects tooling is worth deleting regardless.

### S0-6 · No reachable privacy policy; ToS points at a third party

`settings_page.dart:186` and `:195` both open `https://www.hattiesburgms.com/hubcitytransit/` —
the agency's marketing page, not under your control, and neither a privacy policy nor a ToS.

`web/privacy.html` exists and is a reasonable location-data policy. **Nothing in the app links
to it.**

The app collects precise location (`providers.dart:143`, a continuous `getPositionStream` at
`LocationAccuracy.high`) and, on the ETA path, transmits user coordinates to Google. Play requires
a policy URL in the listing and, for location-accessing apps, an in-app accessible policy.
Data Safety must declare precise location truthfully.

### S0-7 · No OSM / CARTO attribution — licence breach

`map_page.dart:495` renders CARTO basemap tiles derived from OpenStreetMap. Grep for
`Attribution|OpenStreetMap|CARTO` across `lib/` returns only the tile URLs. ODbL requires OSM
attribution; CARTO's ToS requires CARTO attribution. `flutter_map` ships `RichAttributionWidget`
for exactly this. Exposure under Play's Intellectual Property policy, and more visible on web
where your origin appears in the `Referer`.

# S1 — The app shows riders wrong information

These are the findings that matter most for a transit app. Each produces confident, plausible,
incorrect output under a LIVE badge.

### S1-1 · GPS→schedule stop mapping is a ratio between lists that do not correspond

`schedule_adjustment_use_case.dart:259`:

```dart
final ratio  = gpsIndex / (gpsCount - 1);
final mapped = (ratio * (scheduleCount - 1)).round();
```

This assumes the GPS stop list and the schedule stop list are the same route sampled uniformly.
Measured from the shipped assets:

| route | GPS stops | schedule stops |
|---|---|---|
| blue | 44 | **50** |
| gold | 13 | **15** |
| green | 17 | **18** |
| orange | 29 | **33** |
| red | 23 | **30** |
| purple | 35 | **37** |
| brown | 33 | 33 |

Six of seven disagree, and the lists are not aligned at the ends: blue's GPS list starts at
schedule index 1 and ends at index 46, not the schedule's terminal index 49. Name-matching blue
shows systematic drift reaching **3 schedule positions** by the end of the loop.

Blue trips run 6:00→7:00 across 50 stops ≈ 1.2 min/stop, so a 3-index error injects **~3.5 minutes
of fabricated delay**. That is well under `maxDeltaMinutes = 15`, so it passes the sanity gate at
`:114`, gets smoothed, and is presented as a live-adjusted arrival. A bus running exactly on time
is shown as three minutes late — worst at the end of the route, where riders care most. There is
no confidence signal and no distance-to-schedule-stop check.

**Fix direction:** an explicit `scheduleStopIndex` on each stop record. This is a data-schema
change; see `REMEDIATION_PLAN.md` P1-1.

### S1-2 · No service calendar — weekends and holidays render weekday times as live

Grepping `lib/` for `weekday|Saturday|Sunday|holiday|serviceDay` returns **zero hits**.
`schedules.json` has no calendar dimension. `_nowMinutes` (`:276`) is `hour * 60 + minute` — the
date is discarded entirely.

Sunday 10:00 AM: `_identifyTrip` matches the weekday trip that would be in progress, `_buildStops`
renders full arrival times, and stops are flagged as already served. If any vehicle — a
maintenance truck, a bus deadheading — produces a fresh ArcGIS fix, `gpsFresh` goes true and the
app shows a smoothed, **LIVE-badged** schedule for service that does not exist.

This is the classic transit-app failure that leaves someone standing at a stop.

### S1-3 · The delta engine cannot tell two buses on the same route apart

`schedules.json` has one `trips` array per **route**, but `transit_ids.dart:53` maps
blue→`[blue1, blue2]` and gold→`[gold1, gold2]`. Blue runs a **30-minute headway from 9:00 AM**
with 60-minute trips — two trips are always concurrently active, one per physical bus.

`adjust()` (`:58-63`) takes no `busId`. `_identifyTrip` picks the trip with the smallest
`now - first`; `_identifyTripByBusPosition` picks the trip closest in time at the snapped index.
Neither is bus-aware.

At 10:15 AM with blue1 mid-trip-4 and blue2 mid-trip-5, tracking blue1 selects trip 5, computes a
~30-minute delta, trips the ±15 gate, and **silently switches the entire live layer off** with no
explanation — or the GPS path picks the other bus's trip and shows blue2's timetable while blue1's
dot moves on the map.

### S1-4 · Fabricated stop IDs shown to riders

`schedule_page.dart:316`:

```dart
Text('Stop ID: ${8120 + entry.index}', …)
```

Invented from the list index. Note the fix is **not** a one-liner: line 316 sits in `_StopRow.build()`,
a different widget class ~140 lines from the `transferMap['${s.stopId}']` use at `:178`, and the
`_Entry` record (`:226-234`) carries `index` but no `stopId`. The real ID must be plumbed through. Every stop on every route displays an ID that
corresponds to nothing on signage or in dispatch.

### S1-5 · Bus marker vanishes on a single failed poll, while the panel claims otherwise

`map_page.dart:405-408`:

```dart
final busLocation = busAsync.asData?.value;
// Use last-known location for offline state (ghost marker)
final effectiveBusLocation = busLocation;
```

The comment promises a ghost marker; the code is a dead alias. `asData` is null for `AsyncError`,
so any transient poll failure removes the bus from the map — while `_BusInfoPanel`
(`map_page_stop_sheet.dart:382`) simultaneously renders "Showing last known position." The two
panels contradict each other on screen.

### S1-6 · One network error kills live tracking for the rest of the session

`providers.dart:71-81` — a `while (true)` inside an `async*` StreamProvider that is **not**
`autoDispose`. `getBusLocation` *throws* on any non-503 `DioException` after its single retry. An
exception inside a generator terminates the stream; Riverpod moves the provider to `AsyncError`
and, because no dependency changed, never rebuilds it.

Ride through one dead-cell pocket and `busStatusProvider` reads `asData?.value` → null →
`BusStatus.offline` **permanently**. The LIVE badge never returns. Recovery requires switching bus
or restarting the app. The `AsyncError` is discarded by `asData?`, so the user is told nothing.

### S1-7 · Onboarding's "Enable Location & Continue" never requests location

`onboarding_page.dart:435` wires the primary CTA to `_next()` — `markOnboardingSeen()` +
`context.go('/map')`. Functionally identical to the "Continue without location" button beside it.

`launch_page.dart:45` compounds it: `await Geolocator.checkPermission()` costs a platform
round-trip and **both branches of the following `if` call `context.go('/map')`**. Dead code.

The OS dialog first appears when the user taps the map FAB — long after being told they had
enabled it.

### S1-8 · The ETA feature is unreachable dead code

`_StopDetailSheet` declares `etaLoading`, `etaRequested`, `etaMinutes`, `etaNearestStop`,
`etaError`, `onGetEta` and `selectedBus` as **required** parameters, and its `build()`
(`map_page_stop_sheet.dart:489-784`) references **none of them**. There is no "Get ETA" button.

Consequences: `_fetchEta` can never fire, the `get_eta_clicked` analytics event never emits, and
~40 lines of state machine in `_MapPageState` are unreachable.

**This changes the risk framing in the original brief.** The "user taps ETA 30 times = 60 billed
Directions calls" scenario is not live. The key leak (S0-1) is real and independent — an attacker
bills your key directly and does not need your app. Urgency is key-leak, not app-driven spend.

Latent inside the dead code, for whoever revives it: `_etaLoading` / `_etaInFlight` /
`_etaRequested` are three booleans encoding one four-state machine, mutated inconsistently
(`_etaInFlight` outside `setState`, `_etaRequested` only on success), with **no stale-response
guard** — switching stops mid-request writes the previous stop's ETA into the new stop's sheet.

# S2 — Cost, performance, resource abuse

### S2-1 · 1,200–2,400 ArcGIS requests per user per hour, running whether or not anyone is watching

`busRefreshInterval = 3s` (`app_constants.dart:4`) on a **non-`autoDispose`** StreamProvider that
is subscribed for the lifetime of the root `ProviderScope`.

- 1,200 req/hour/user. The retry interceptor doubles it to **2,400** against a failing
  endpoint — amplifying load exactly when the server is already degraded.
- Nothing pauses it. No `WidgetsBindingObserver`, no `AppLifecycleState` gating anywhere in
  `lib/`. It runs while the user is on Settings and while the app is backgrounded on Android.
- `MapPage` sets `wantKeepAlive` **and** lives in an `IndexedStack`, so it never disposes.
- 8-hour ride day ≈ 9,600 requests per device. 500 concurrent riders ≈ 600k–1.2M requests/hour
  against a public ArcGIS FeatureServer.

### S2-2 · The map rebuilds ~4,286 `LatLng` objects every 3 seconds, forever

`map_page.dart:358-365` reconstructs all seven route polylines inside `build()`, which the 3s poll
drives unconditionally. Red and purple alone are 1,881 and 1,878 points.

Per rebuild: 4,286 validity predicates (up to 10 comparisons each), 4,286 `LatLng` allocations, 7 list
allocations, 7 `Polyline` allocations. That is **~86,000 allocations/minute, ~5.1M/hour**, on a
page that never disposes — including while the user is on another tab.

The polylines change only when `routesProvider` or `selectedRoute` changes.

### S2-3 · `_getRouteSlice` runs two full haversine scans inside `build()`

`map_page.dart:141-180`, called at `:344`. Two linear scans over the raw polyline, each computing
a full haversine (4 trig + `sqrt` + `atan2`). For a red or purple trip: **3,762 haversine
evaluations ≈ 15,000 trig calls per rebuild**, every 3s while a trip is active. The result depends
only on `(polyline, boardStop, destStop)` — all frozen for the life of the trip.

### S2-4 · Assets re-parsed 7× at startup on the UI isolate

`_loadStops` checks `_stopsCache != null` **before** the `await` but assigns **after** it.
`allStopsByRouteProvider` fires `Future.wait` over all 7 routes, so seven `_loadStops()` calls
interleave before any populates the cache — `stops.json` is decoded seven times on the main
isolate, all racing to overwrite `_stopsCache`. No in-flight dedupe.

`getRoutes` has **no cache at all** and re-parses `routes_wgs84.json` (~4,300 coordinate pairs)
synchronously on every call.

### S2-5 · Nominatim: policy violations and a plausible ban

- **User-Agent** (`nominatim_service.dart:30`) is `'HubCityTransitApp/1.0'` with **no contact
  address**, and is skipped entirely on web — where browsers
  [forbid setting it](https://fetch.spec.whatwg.org/#forbidden-request-header) regardless. OSM
  policy requires an identifiable client *with a way to reach the operator*.
- **Rate:** realistically 3–5 requests per destination lookup, one per typing pause. (An earlier
  draft claimed a sustained 1.67 req/s — wrong: `map_page.dart:198` cancels the pending timer on
  every keystroke, so continuous typing generates zero requests until the user pauses.)
- **Two independent `NominatimService` instances** (`map_page.dart:77`,
  `map_page_navigation.dart:44`), each with its own `Dio`, no shared limiter or queue, both
  bypassing `dioProvider` entirely — no timeouts, no interceptors, no retry. The service itself
  *is* injectable (`NominatimService({Dio? dio})`); it is the two widget-state call sites that
  cannot be overridden in a test.
- No result caching, no `email=` parameter, no backoff on 429.
- OSM's policy explicitly names autocomplete-style querying as prohibited.

Enforcement is an IP/origin block that would take out geocoding for **both** web and mobile
clients simultaneously.

### S2-6 · Typewriter placeholder calls `setState` 20–33× per second, permanently

`map_page_stop_sheet.dart:1044-1077`. `_tick` reschedules at 50ms (typing) / 30ms (deleting) and
never terminates — `_phraseIdx` wraps and `:1072` forces it back to 1, so the cycle is infinite.
Because `MapPage` is kept alive in an `IndexedStack`, it runs for the entire session including
while the user is on Settings. The frame scheduler never idles → continuous vsync wakeups and
measurable battery drain. The `Future.delayed` is not stored, so it is uncancellable.

Adjacent: `AnimatedOpacity` with a 400ms duration is restarted every 30–50ms (`:1106`), so it
never reaches its target — an animation object churned ~25×/s to produce a cursor that never
visibly blinks.

### S4-2 · Layering violations

- **Domain imports data**: `transit_repository.dart:1-5` imports five models from `data/models/`.
  The dependency arrow points the wrong way.
- **Use case imports data models**: `schedule_adjustment_use_case.dart:2-3` — the delta engine is
  coupled to freezed codegen.
- **Flutter in `core/constants`**: `route_metadata.dart:1` imports `material.dart` for `Color`.
- **Domain logic in the app layer**: `deriveBusStatus` / `BusStatus` (`providers.dart:227`) are
  pure rules living in a file importing `material.dart`, `flutter_compass`, `geolocator`,
  `shared_preferences`.
- **Unmockable seams**: `NominatimService` `new`ed in widget state; `rootBundle` called directly
  in the repository with no `AssetBundle` injection; `DateTime.now()` inside providers;
  `SharedPreferences.getInstance()` called directly in three `StateNotifier`s plus a `FutureProvider` and a free function.
- **Duplicated haversine**: `transit_repository_impl.dart:382` re-implements
  `core/utils/haversine.dart`.

### S4-3 · Scalability — a route cannot be added without code changes

Four separate places hardcode the route set:

1. `transit_ids.dart` — `enum RouteId`, `enum BusId`, `routeBusMap`.
2. `transit_ids.dart:41` `busIdToRouteId` hardcodes `startsWith('blue')`/`startsWith('gold')`;
   `transit_repository_impl.dart:271` `_routeIdForBus` **duplicates the same logic independently**.
3. `route_metadata.dart` — three `Map<RouteId, …>` literals. Because they are maps rather than
   exhaustive switches, a missing entry is **not a compile error** — it is a runtime crash.
4. `core/utils/transfer_connections.dart` — **43 keys / 47 connection tuples** hand-written and
   keyed by `'route-stopId'` strings, with no validation that the referenced stops exist.

A **schedule change** is worse: `schedules.json` is a bundled asset with no remote fetch and no
version field, so any timetable revision requires a full store release.

A **second agency** is not expressible: no agency dimension in any asset, and
`transit_repository_impl.dart:57` embeds the operator in the ArcGIS query —
`"LOWER(full_name) = 'hct ${busId.toLowerCase()}'"`. That `where` clause is also built by string
interpolation; enum-derived today, one refactor away from taking user input.

### S4-4 · Latent time bugs

- **Midnight rollover**: `parseTimeToMinutes` and `_nowMinutes` work in a 0–1439 space with no
  date. Currently latent — the assets never cross midnight (latest stop 18:30). The moment a
  late-night route is added, a trip running 23:40→00:20 fails `_identifyTrip`'s range check, and
  `rawDelta` computes 00:05 minus 23:55 as **−1430 minutes** instead of +10, tripping the ±15 gate
  and silently disabling live mode.
- **DST**: `DateTime.now()` is local wall-clock. Hattiesburg observes DST; there is no
  `serviceDate` concept to build on.
- **Arrivals filter** has the same midnight wrap bug today: a 00:15 trip parses to 15, less than
  `nowMinutes` all evening, so late-night service is classified as past.
  (`map_page_stop_sheet.dart:863`)
- `parseTimeToMinutes` rejects 24-hour input — a schedule authored as `"14:30"` silently becomes
  NaN and the trip is skipped with no error surfaced.
- `smoothingFactor = 0.85` is applied once per computation, not as a recursive EMA. It is a flat
  15% shrink toward on-time, not smoothing. It holds no state, so it cannot damp GPS jitter across
  poll ticks — the displayed delta jumps freely every 3s.

### S4-5 · "Between trips" renders a blank schedule with no explanation

`adjust()` returns `tripIndex: -1` and `_buildStops(…, null, …)` emits `scheduledTime: ''` for
every stop. At 7:15 PM (after blue's last trip ends at 6:30) the schedule page renders 50 rows
with **blank times**, nothing marked past, and no "service has ended for today" or next-day first
departure. Same before 6:00 AM and all weekend.

### S4-6 · Matching by fuzzy substring

Both the schedule page (`schedule_page.dart:219`) and the stop sheet
(`map_page_stop_sheet.dart:847`) match stops by bidirectional substring on normalised names:
`s.contains(n) || n.contains(s)`. `"main"` matches `"Main St at 7th"` and vice versa, and the
sheet takes the **first** match via `break`, not the best. Produces wrong transfer badges and
wrong arrival times. Both should key on `stopId`.

### S4-7 · Dead code and unused dependencies

- **Unused packages** (5): `connectivity_plus`, `google_fonts`, `intl`, `logger`,
  `cupertino_icons` — zero imports each.
- **Dead provider**: `onboardingSeenProvider` — zero consumers.
- **Dead parameter**: `_SettingsTile.isFirst` — declared, stored, passed three times, never read.
  One call site computes `isFirst: kIsWeb` to feed nothing.
- **Dead widget**: a `GestureDetector` with no callbacks wrapping the location FAB
  (`map_page.dart:728`).
- **Dead branch**: `launch_page.dart:48-53`, both arms identical.
- **Dead API surface**: `findTransferConnections` accepts `allStopsByRoute` and `thresholdMeters`
  and ignores both — the body admits it in a comment.
- **Filler comments**: `// Logo`, `// Hero`, `// Page title`, `// Skip button`, `// Dots + button`,
  `// Route color row`, `// Description`, `// App Info`, plus dartdoc referencing the deleted
  `MainScaffold`.
- No `TODO`/`FIXME` markers anywhere **in `lib/` or `test/`** (one exists at
  `android/app/build.gradle.kts:31`) — the incomplete work (permissions, notifications, ToS) is
  unmarked rather than tracked.
- **Fare data hardcoded inside a widget** (`settings_page.dart:203-256`) — a fare change requires
  a store release.
- **Inaccurate copy**: About attributes data to "the Hub City Open Data Portal and regional
  transit authority APIs"; the actual sources are one ArcGIS URL and three bundled JSON files.

### S4-8 · Settings persistence has a real lost-write race

`ThemeModeController`, `DarkBasemapController`, and `FavoritesNotifier` all set a synchronous
default in the constructor, then fire-and-forget an async `_load()` that overwrites `state`:

- **Flash of wrong state** on every cold start, very visible behind the 2.2s splash.
- **Lost writes**: tapping a theme pill while `_load()` is in flight is silently reverted when
  `_load()` completes.
- No `try`/`catch` — a SharedPreferences failure leaves the controller stuck on its default with
  no signal.

This also matters for the announcements work: the established pattern is one hand-written
`StateNotifier` + one hardcoded prefs key per toggle, with `'onboarding_seen'` duplicated as a
string literal across two files (`providers.dart:218,223`, `launch_page.dart:37`). N notification channels under this pattern means N classes and
N keys. A typed preferences layer should land first.

# Web-readiness (retiring the Next.js client)

The web build runs, and real effort went into it (`1df3e01`, `fd84719`, `a1afd49`, `47f0781`).
It is not yet a replacement.

| # | Issue |
|---|---|
| **W1** | **`env.txt` becomes a public download.** See S0-1. Do not deploy web until it leaves the asset bundle. |
| **W2** | **ETA cannot work on web.** Google Directions Web Service sends no CORS headers and is documented as not for browser use. 100% of web users get "Could not calculate directions." Needs the JS Directions Service or a server endpoint. (ArcGIS is fine — it sends `Access-Control-Allow-Origin: *`.) |
| **W3** | **No viewport meta tag** in `web/index.html` (`grep -c viewport` → 0). Mobile browsers render at a ~980px virtual viewport and scale down — unusable on phones, which is most transit web traffic. One line. |
| **W4** | **Broken SVG namespace** in the web splash: `xmlns="http://www.000101.com/svg"`. Collateral damage from a global find-and-replace of the brand token `#000101` across the string `w3.org/2000`. The icon does not render. Introduced in `47f0781`. |
| **W5** | **User-Agent cannot be set on web** — the existing `kIsWeb` guards are correct, and one was just reverted in the working tree (S0-5). Restore it. |
| **W6** | `flutter_compass` is android+ios only — the heading cone is silently absent. Guard at `providers.dart:25` is correct. `DeviceOrientationEvent` is a possible web-only implementation, but net-new work. |
| **W7** | `geolocator_web`: `isLocationServiceEnabled()` always returns true; `distanceFilter` is ignored (more rebuilds); `openAppSettings()` throws — correctly guarded at `settings_page.dart:138`. |
| **W8** | Tile requests are not cancelled on pan — dozens of doomed requests queue against the browser's 6-connections-per-host limit. |
| **W9** | **No SEO.** Flutter Web renders to canvas; there is no crawlable DOM. Ranking for "Hattiesburg bus schedule" would be lost. Decide deliberately. |
| **W10** | Browser tabs throttle background timers to ~1/min, so the 3s poll won't spin at full rate when hidden — but resumes instantly on focus. An open tab is a persistent load generator. |

**Conclusion: a small server tier cannot be retired.** It is the only place a key can live, the
only place a `User-Agent` can be set, and the only place a rate limit means anything. Keep the
Next.js `/api/*` handlers (or equivalent edge functions), retire only the UI, and point both
Flutter clients at them — which also fixes the mobile key leak.
